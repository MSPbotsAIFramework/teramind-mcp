## Requirement understanding

One line: Build a Teramind MCP connector so the Agent platform can review computer/user inventory, alerts, and behavior-policy data from Teramind for insider-threat monitoring.

Teramind is an insider-threat / employee-monitoring product. The ticket asks for a read-oriented
integration that lets an Agent platform tenant pull three categories of data out of their Teramind
account: (1) the inventory of monitored computers and users, (2) security alerts raised by Teramind's
rule engine, and (3) the behavior-policy configuration (the rules/policies that define what counts as
risky behavior) — so an agent can summarize or reason over this data without a human opening the
Teramind console. The ticket carries no further detail beyond the one-line description and a link to
an internal integration-request page (`conduit.wyre.ai/plugins/teramind`); see Sources below for what
that page does and does not add.

## Product design

### Goals / Non-goals

**Goals (this ticket, v1):**
- Expose monitored-computer inventory (list + detail) as MCP tools.
- Expose monitored-user/agent inventory (list + detail) as MCP tools.
- Expose alerts for a given time window, plus a way to resolve the human-readable rule name/description
  behind an alert, as MCP tools.
- Expose behavior-policy configuration — policies, the groups/entity-structure they are organized
  under, and the anomaly-rule catalog that policies are built from — as MCP tools, so an agent can
  explain *why* a given alert fired and what the customer currently monitors for.
- All v1 tools are **read-only**. See "Decisions made by DEV01" for why.

**Non-goals (this ticket):**
- No write/delete tools (creating/deleting computers or agents, enabling/disabling monitoring,
  creating/updating/deleting policies or anomaly rules, importing/exporting policy files). The ticket
  only asks to "review" data; nothing in the description or the linked integration page asks for
  configuration changes from the agent side.
- No coverage of Teramind areas unrelated to the three named capabilities: BI/reporting grids and
  charts, time-tracking reports, scheduling, LDAP sync, SMTP test, licensing, video export/session
  replay, departments, player/timeline tags, voip-event ingestion. These exist in the vendor API but
  are outside "computer/user inventory, alerts, behavior-policy data".
- No webhook/streaming ingestion of alerts — Teramind's API is pull-only for the resources in scope;
  this connector is a request/response MCP server, consistent with every other connector on the
  platform (SOP "running model": stateless, Gateway-driven).
- No change to the Agent platform UI or connector catalog page itself — that page already lists and
  connects any MCP connector generically (wiki, "Connector detail view" above); nothing here changes it.

### Acceptance criteria

- **AC1** — Given a tenant has connected the Teramind connector with a valid instance host and access
  token, When an agent calls the "list computers" tool, Then it receives the tenant's monitored-computer
  inventory (id, name, status/online, department where available) without needing direct access to the
  Teramind console.
- **AC2** — Given a computer id from AC1, When the agent calls the "get computer" tool, Then it
  receives that computer's full detail record.
- **AC3** — Given the same connected tenant, When the agent calls the "list agents" tool (agents =
  Teramind's term for monitored users), Then it receives the user inventory (id, name, email, online
  status); When it calls "get agent" with an id from that list, Then it receives that user's detail
  record.
- **AC4** — Given a start and end time, When the agent calls the "list alerts" tool, Then it receives
  the alerts raised in that window, each identifying the triggering rule, the agent/computer involved,
  and the timestamp.
- **AC5** — Given one or more alert rule ids returned by AC4, When the agent calls the "describe alert
  rules" tool, Then it receives the human-readable name/description for each rule id, so an alert can
  be explained without opening the Teramind UI.
- **AC6** — Given the tenant's behavior-policy configuration, When the agent calls the "list behavior
  policies", "get behavior policy", "list behavior groups", or "list anomaly rules" tools, Then it
  receives the policy/group/rule structure the customer uses to define risky behavior.
- **AC7** — Given the connector is called without credentials, or with an instance-host value that is
  not a Teramind-owned hostname, When any tool is called, Then the call is rejected (401 for missing
  credentials; a structured `invalid_argument` error for a disallowed host) instead of being silently
  proxied to an arbitrary host. (This is a deliberate SSRF guard — see Decisions.)
- **AC8** — Given the upstream Teramind API is unreachable, times out, or returns a 5xx/429, When any
  tool is called, Then the tool returns the structured error envelope (`upstream_error` or
  `rate_limited`, with `retryable` set appropriately) rather than raising an unhandled exception.
- **AC9** — Given a list tool's result would exceed the default page size, When the agent calls it
  without an explicit limit, Then the response is truncated to the default limit with `has_more: true`,
  and the agent can request more with an explicit higher `limit` (no native cursor exists upstream for
  these resources — see Decisions).
- **AC10 (multi-tenant isolation)** — Given two concurrent requests carrying two different tenants'
  Teramind instance/token headers, When both are in flight at the same time, Then neither request's
  response, logs, or error output contains the other tenant's instance host, token, or data. This must
  be verified at the tool/HTTP layer (request-scoped `ContextVar`, not a flag hidden behind UI), since
  there is no UI in this connector to gate on.

### Open questions

- [non-blocking] Should "list computers"/"list agents" expose Teramind's `department_id` as a filter (the
  agents endpoint's `fields` parameter allows requesting it, but filtering by it is not documented) —
  v1 ships without a department filter; add later if a concrete tenant asks for it.
- [assumed] The ticket does not say whether write/configuration tools (creating anomaly rules, disabling
  monitoring on a computer, etc.) are wanted eventually. This design assumes **read-only is the full
  intended scope for now** (see Decisions) — if that assumption is wrong, section "Goals / Non-goals"
  and the tool list in Tech design §4 need to be redone with a write-tool threat model (deliberate
  destructive-tool gating, audit logging, etc.), which is a materially different and larger design.

## Tech design

### Conclusion

New MCP server, `MSPbotsAIFramework/teramind-mcp` (currently an empty scaffold). Built from scratch
against Teramind's public Postman-published API doc (clean-room, main line A — no existing repo to
extend). Ten read-only tools across four resource groups (computers, agents, alerts, behavior-policy
data), one Streamable HTTP service, FastMCP + httpx + pydantic, following the same shape as other
MSPbotsAIFramework vendor connectors. Credentials are two per-request headers (instance host + access
token); the instance host is validated against Teramind's own domain to close an SSRF hole, since this
connector's whole purpose is handling security-sensitive data.

Nothing yet — `README.md:1-2` is the only file in the repo (`b95db34`, scaffold commit by Cavin Lang).
No code, no `pyproject.toml`, no tests exist to build on. This is a from-scratch build, not a
modification.

Nearest same-shape reference inside the org (read for conventions only, not copied — different vendor,

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Thin per-resource tools (chosen) | One tool per upstream resource/verb pair (list/get), grouped by the ticket's three capability areas | Matches ticket scope exactly; small tool surface (10, well under the 20 cap); each tool maps 1:1 to one documented upstream endpoint, so the contract is easy to verify against the vendor spec | Agent has to make 2+ calls to correlate an alert with its rule description (no server-side join) | Chosen — ticket explicitly scopes to "review ... data", not "build a Teramind console"; joining data server-side would be guessing at a UX need nobody asked for |
| B. One generic `teramind_request(method, path, params)` passthrough tool | Single tool, proxies arbitrary Teramind API calls | Minimal code, covers the whole API without picking tools | Violates SOP §2 ("tools are capabilities, not a mirror of the API"); no way to apply the read-only policy at the tool boundary (an agent could call any write endpoint through it); defeats the per-tool `readOnlyHint`/description contract the platform relies on | Rejected — this is the one option the SOP explicitly rules out, and it removes the read-only guarantee that is the main safety property of this design |
| C. Server-side alert enrichment (alerts come back with rule descriptions already joined) | `list_alerts` calls `alerts/descriptions` internally and merges | Fewer round trips for the agent | Extra upstream call on every `list_alerts` invocation even when the agent doesn't need descriptions (token/latency cost in SOP §5); couples two independently-paginated resources | Rejected for v1 — kept as two tools (AC4 + AC5); revisit if a future ticket shows agents always calling both together |

### Data & API contract

All upstream calls use base `https://<X-Teramind-Instance value>` and header `x-access-token:
<X-Teramind-Access-Token value>`. Upstream responses are summarized from Teramind's published Postman
collection (`https://apidoc.dev.teramind.co/`, collection id `12825404`, publish id `TW74jRAB`,
fetched 2026-11-02); exact upstream field sets beyond what's shown below will be confirmed against live
responses during implementation (no test account yet — see "No test account" in Non-functional/Test
strategy), but the resource shapes, auth header, and URL paths are from the vendor's own published
reference, not invented.

**`teramind_list_computers`** — readOnlyHint
- Upstream: `GET /tm-api/computer`
- MCP args: `limit` (default 50, max 200), `cursor` (opaque, see pagination note below)
- MCP response: `{"computers": [{"id", "uid", "name", "online", "department_id"}...], "has_more": bool,
  "next_cursor": str|null}`

**`teramind_get_computer`** — readOnlyHint
- Upstream: `GET /tm-api/computer/:id`
- MCP args: `computer_id` (required)
- MCP response: full computer record (id, uid, account_id, name, and the remaining fields Teramind
  documents for this endpoint); `not_found` error if the id does not exist for this tenant.

**`teramind_list_agents`** — readOnlyHint
- Upstream: `GET /tm-api/v1/agents?fields=...`
- MCP args: `limit`, `cursor`, optional `fields` (comma-separated passthrough of the upstream `fields`
  allow-list, e.g. `department_id,status,position`)
- MCP response: `{"agents": [{"agent_id", "name", "email_address", "online", ...requested fields}...],
  "has_more", "next_cursor"}`

**`teramind_get_agent`** — readOnlyHint
- Upstream: `GET /tm-api/v1/agents/:id?fields=...`
- MCP args: `agent_id` (required), optional `fields`
- MCP response: single agent record; `not_found` if the id does not exist.

**`teramind_list_alerts`** — readOnlyHint
- Upstream: `GET /tm-api/v1/alerts?periodStart=<ISO>&periodEnd=<ISO>`
- MCP args: `period_start`, `period_end` (both required, ISO 8601 — upstream documents these as
  required; `invalid_argument` if either is missing or not parseable), `limit`, `cursor`
- MCP response: `{"alerts": [{"id", "timestamp", "agent": {"id","name"}, "computer": {"id","name"},
  "rule_id", ...}...], "has_more", "next_cursor"}`

**`teramind_describe_alert_rules`** — readOnlyHint
- Upstream: `POST /tm-api/v1/alerts/descriptions` body `{"ids": [...]}`
- MCP args: `rule_ids` (required, list of ints, max 100 per call — chosen to bound the upstream POST
  body size; no upstream-documented max, this is a defensive MCP-layer cap)
- MCP response: `{"descriptions": [{"id", "name", "description"}...]}`

**`teramind_list_behavior_policies`** — readOnlyHint
- Upstream: `GET /tm-api/behavior-policy`
- MCP args: `limit`, `cursor`
- MCP response: `{"policies": [{"behavior_policy_id", "behavior_group_id", "entity_group_id",
  ...}...], "has_more", "next_cursor"}`

**`teramind_get_behavior_policy`** — readOnlyHint
- Upstream: `GET /tm-api/behavior-policy/:id`
- MCP args: `policy_id` (required)
- MCP response: full policy record including its rule definition; `not_found` if missing.

**`teramind_list_behavior_groups`** — readOnlyHint
- Upstream: `GET /tm-api/behavior-group`
- MCP args: `limit`, `cursor`
- MCP response: `{"groups": [{"behavior_group_id", "entity_group_id", "name"}...], "has_more",
  "next_cursor"}`

**`teramind_list_anomaly_rules`** — readOnlyHint
- Upstream: `GET /tm-api/behavior-rule`
- MCP args: `limit`, `cursor`
- MCP response: `{"rules": [{"behavior_rule_id", "name", "account_id", ...}...], "has_more",
  "next_cursor"}`

**Error envelope (all tools, on failure):**
```json
{"error": {"code": "unauthorized|not_found|invalid_argument|rate_limited|upstream_error",
           "message": "<human-readable, no secrets>", "retryable": true|false}}
```

**Pagination note**: none of the six `list_*` upstream endpoints above documents a native
`limit`/`offset`/cursor parameter in Teramind's published collection (confirmed by reading each
endpoint's request-parameter table — only `agents` and `alerts` document any query parameters at all,
and those are `fields` and the required time window, not pagination). So pagination is applied at the
MCP layer: the full upstream list is fetched once, then truncated to `limit` with `has_more` computed
from whether more rows existed. `cursor` is an opaque offset into that fetched list, not a protocol the
agent needs to understand beyond "pass back `next_cursor`". If a future round finds a tenant with a
large enough inventory that fetch-then-truncate is too slow/expensive, revisit against Teramind
support — this is a decision made without a live account to verify response sizes against (see
Decisions).

**DB**: none — this service is stateless and holds no database.

**Backward compatibility**: not applicable — first version, nothing to be compatible with.

### Key flow / sequence

```
Agent → Gateway → teramind-mcp /mcp (tools/call: teramind_list_alerts)
                     │
                     ├─ auth.py middleware: read X-Teramind-Instance + X-Teramind-Access-Token
                     │   → validate instance host → set ContextVar → (missing/invalid → 401/invalid_argument, stop)
                     ├─ tools/alerts.py: validate period_start/period_end
                     ├─ client.py: GET https://<instance>/tm-api/v1/alerts?periodStart=..&periodEnd=..
                     │   headers: x-access-token: <token>
                     │   (timeout/retry/backoff per errors.py; 429/5xx → mapped error)
                     └─ response → truncate to limit, compute has_more → return to Agent
                     finally: ContextVar reset
```

### Non-functional

- **Idempotency & concurrency**: every tool is a read, so idempotency is inherent (GET/POST-read, no
  side effects). Concurrency: each request builds its own httpx client and reads credentials from its
  own `ContextVar` snapshot — no shared mutable state between concurrent requests (SOP §3.3/§3.4),
  verified by AC10 / `tests/test_middleware.py`.
- **Performance**: Teramind inventories for a monitored-employee product are expected to be in the
  hundreds-to-low-thousands range per tenant (no live account to confirm — flagged as an assumption).
  Fetch-then-truncate (see pagination note) keeps the MCP response bounded regardless of upstream size;
  the upstream fetch itself is not currently bounded, which is the main performance risk this design
  accepts for v1.
- **Security**: this is the main risk surface of the whole ticket — Teramind data is explicitly
  insider-threat-monitoring data (employee activity, alerts, behavior policies). Three concrete
  controls: (1) credentials only ever read from the two request headers, never logged, never written to
  disk/env, matching the three iron laws; (2) **instance-host SSRF guard** — `X-Teramind-Instance` is
  validated to match a hostname pattern ending in `.teramind.co` (or, as a documented escape hatch, a
  tenant-configured custom domain allow-list if a future ticket needs on-prem Teramind — out of scope
  for v1, rejected with `invalid_argument` until then) before it is ever used to build an outbound URL,
  so this connector cannot be used as an open proxy to arbitrary hosts; (3) all ten tools are read-only
  — there is no tool in this service that can change a customer's Teramind configuration or disable
  monitoring, which bounds the blast radius of a compromised or over-eager agent to "read more than it
  should", not "change the customer's security posture" (see Decisions for why this is v1's scope, not
  an oversight).
- **Multi-tenant isolation**: AC10. No module-level/global state holds credentials; everything flows
  through the request-scoped `ContextVar` set by `auth.py` and reset in a `finally` block.
- **Observability**: log tool name, upstream status code, and error `code` (never the access token or
  full response body) per call; `/health` only checks the process is up (no upstream dependency, per
  SOP §1.1) so it can't be used to probe whether a given Teramind instance is reachable.

### Risks & dependencies

- **Risk**: Teramind's actual response fields may differ from the Postman collection's documented
  examples (the collection is vendor-maintained but response examples can drift from the live API).
  Mitigation: tests are written against the documented shapes; note in README/report that live-field
  verification is pending a real account.
- **Risk**: the SSRF-guard hostname allow-list (`*.teramind.co`) may be too strict if a customer runs a
  self-hosted/custom-domain Teramind instance. Mitigation: documented as a v1 limitation in Decisions;
  rejecting with a clear `invalid_argument` message is safer than silently allowing arbitrary hosts, and
  the allow-list can be extended later with a real case in hand.
- **Dependency**: none on other tickets or repos. `mcp-service-gateway` (read-only reference only) is
  unaffected — this is a standard credential-header vendor connector, no gateway change needed.
- **Release order**: no dependency — this is the only repository this ticket touches.

### Decisions made by DEV01

- **Read-only v1 scope** — the ticket says "review"; nothing asks for configuration changes. Chose to
  ship zero write/delete tools rather than include them "for completeness". Alternative considered:
  mirror every upstream verb (SOP explicitly warns against this — "tools are capabilities, not an API
  mirror" — and for a security-monitoring product, shipping delete/disable-monitoring tools nobody
  asked for is a real risk, not a convenience).
- **Two-header auth: instance host + access token** — Teramind's API is per-instance (`{{teramind_instance}}`
  in the vendor's own collection) and the one documented auth mechanism is a single `x-access-token`
  header; there is no account-identifying header separate from the instance host. Alternative
  considered: bake a single instance into server config — rejected, violates "credentials only from
  Header, no env fallback" and would make the service single-tenant.
- **SSRF guard restricting `X-Teramind-Instance` to `*.teramind.co`** — without this, the header is an
  attacker-controlled URL host and the service becomes an open outbound proxy. Alternative considered:
  no validation (trust the Gateway/tenant) — rejected as inconsistent with "this connector exists
  specifically to handle security-sensitive data"; a wrong default here is exactly the kind of
  assumption that should be made explicit rather than silently picked.
- **Client-side pagination (fetch full list, truncate, `has_more`)** — none of the in-scope list
  endpoints document upstream pagination. Alternative considered: no `limit`/truncation at all (return
  everything) — rejected per SOP §A4 token-economy rule ("list tools must have a limit, never
  unbounded").
- **`alerts/descriptions` kept as a separate tool rather than auto-joined into `list_alerts`** — see
  Option analysis C. Keeps the common "just give me alerts" path cheap; an agent that wants
  descriptions makes one extra call.
- **Anomaly rules (`behavior-rule`) and behavior policies (`behavior-policy`) both exposed, as two
  resources rather than one** — Teramind's own API keeps these as separate endpoints (rules are a
  reusable catalog; policies assign rules to an entity group); the ticket's phrase "behavior-policy
  data" is read as covering both, since both live under Teramind's "Behavior Policies" UI area. If this
  reading is wrong and the requester only meant one of the two, that is a scope question for product,
  not a blocking one for this design — flagged as an open-but-non-blocking assumption rather than a
  product-decision blocker, since shipping both is a superset, not a wrong guess that needs undoing.
